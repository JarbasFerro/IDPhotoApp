# 01 — Product definition

## 1. Purpose

ID Photo App is a native iPhone application that helps a person create an identity photo matching the measurable requirements of a selected country and document type, while making the limits of automated validation explicit.

The product should replace the frustrating workflow of searching for dimensions, trying generic photo editors, guessing at head position/background rules, and arranging copies manually for printing.

## 2. Product promise

**From ordinary portrait to correctly formatted ID photo, privately on iPhone, with clear guidance and native Apple-quality interaction.**

The application must optimize for trust. A technically polished image that violates an official requirement is a product failure. A warning that says “we cannot validate this automatically” is preferable to a false green check.

The product is intentionally iOS-only. We are choosing platform depth over platform breadth.

## 3. Product quality bar

The target is not merely “good enough for the App Store.”

The product should be credible as an Apple Design Award / WWDC-quality example of:

- clear purpose and focused scope;
- excellent native iOS interaction design;
- meaningful use of current Apple platform capabilities;
- privacy-preserving on-device processing;
- responsive camera and image workflows;
- thoughtful accessibility;
- polished motion, haptics, typography, iconography, and state transitions;
- robust error recovery;
- deterministic technical correctness;
- restraint: no feature exists only to demonstrate an API.

Apple’s current design principles—purpose, agency, responsibility, familiarity, flexibility, simplicity, craft, and delight—should be used as a design-review lens throughout development.

## 4. Primary jobs to be done

### JTBD-01 — Create a digital ID photo

When I need a passport, visa, ID card, licence, permit, or other document photo, I want the app to format my portrait to the required dimensions and composition so that I can submit the file digitally.

### JTBD-02 — Create printable copies

When I need physical photos, I want the app to place correctly sized copies on common paper/photo formats so that I can print them without manually measuring or arranging anything.

### JTBD-03 — Know what is wrong before submission

When my photo is unlikely to meet the selected requirements, I want specific guidance so that I can retake or fix the photo before I submit it.

### JTBD-04 — Preserve privacy

When I use an image of my face or my child’s face, I want the workflow to work without an account and without uploading the image unless a clearly explained optional feature genuinely requires it.

### JTBD-05 — Feel confident using the camera

When taking a new photo, I want calm real-time guidance on framing, lighting, distance, and obvious problems so I can capture a usable source instead of learning only after the photo is taken.

## 5. Target users

The product should work for:

- adults creating their own ID/document photos;
- parents creating photos for babies or children;
- immigrants/travellers preparing visa or residence-permit photos;
- users who need a professional headshot/CV format but not an official government document;
- users who need several physical copies from one image;
- occasional users who may not understand photo terminology;
- VoiceOver, Voice Control, Dynamic Type, and reduced-motion users who should not receive a degraded core workflow.

The UI must assume low domain knowledge. Terms such as “crown-to-chin,” “pixel density,” or “biometric” require plain-language explanations.

## 6. Product principles

### P-01 — Trust before conversion

Do not place ads, upsells, or paywalls inside the critical correction path. If monetization exists, the user must still understand what is wrong with the image before being asked to pay.

### P-02 — Official source over crowdsourced rule

Every document profile should identify where its requirements came from and when they were last reviewed. Unsourced specifications cannot be published as “official.”

### P-03 — Deterministic geometry

Final dimensions, crop rectangles, print layouts, margins, and DPI metadata must be generated by deterministic code, not by a generative model.

### P-04 — Intelligence assists; it does not redefine identity

Automation may detect the face, estimate landmarks, segment the subject, identify likely quality problems, explain warnings, and suggest corrections. It must not cosmetically alter facial identity for an official-photo workflow.

### P-05 — Reversible editing

The source image is immutable. Every edit must be reproducible from parameters and removable without quality loss from repeated re-encoding.

### P-06 — Internationalization is structural

Country, language, measurement units, paper size, date format, decimal separator, and supported document types are data/configuration concerns, not hard-coded UI assumptions.

### P-07 — Native before custom

Use standard SwiftUI/iOS behavior where it solves the problem well. A custom control must justify why the system control is insufficient.

### P-08 — Content before chrome

The person’s photo, the rule guidance, and the result are the primary content. Navigation and controls should recede when not needed.

### P-09 — Accessibility is product behavior

No critical action may depend solely on drag, pinch, visual alignment, color, or animation. Accessibility alternatives are specified at feature-design time.

### P-10 — Latest platform features need a reason

Use iOS 27, Apple Intelligence, App Intents, Liquid Glass, advanced Vision APIs, or other current technologies only when they reduce friction, improve privacy, increase clarity, or create meaningful delight.

## 7. Core user journey

The intended fast path is:

1. Launch.
2. Choose country/document profile, or invoke a common profile through Siri/Shortcuts where configured.
3. Review a concise requirement summary.
4. Take a photo with the guided AVFoundation camera or select one using PhotosPicker.
5. Local Vision analysis runs.
6. User receives one of three overall states:
   - **Ready** — measurable requirements appear satisfied.
   - **Needs review** — warnings or human judgement remain.
   - **Retake recommended** — source quality is likely inadequate.
7. Automatic crop/background/alignment preview is shown.
8. User adjusts only if necessary.
9. User chooses digital export or print sheet.
10. Native save/share/print flow completes the task.

Target: a valid source photo should require only a few deliberate actions after document selection.

## 8. MVP scope

### 8.1 Included

- Native iPhone app.
- SwiftUI-first interface.
- Country + document profile selection.
- Search and favourites/recent document profiles.
- AVFoundation camera capture with useful real-time guidance.
- PhotosUI/PhotosPicker import without requiring broad Photo Library access.
- HEIC/JPEG handling and orientation normalization.
- Vision face detection.
- Basic landmark/head geometry estimation where reliable.
- Multiple-face detection and blocking guidance.
- Blur/sharpness screening.
- Exposure screening.
- Basic face-size/head-position checks where measurable.
- Vision-based background segmentation/removal where permitted.
- Background replacement with rule-approved colours where applicable.
- Manual crop/position correction.
- Accessible move/zoom controls in addition to gestures.
- Manual or iOS 27-assisted background-mask refinement where quality is sufficient.
- Rule-driven digital export.
- JPEG and PNG where appropriate.
- Print-sheet generator for defined common paper sizes.
- Native share/save/print mechanisms.
- Requirement checklist.
- Source/provenance display for document rules.
- Offline core workflow.
- String Catalog localization architecture.
- Complete accessibility baseline for the primary workflow.
- Privacy manifest and minimal-permission design from the start.
- App Intent proof for high-value entry actions.
- Crash/performance instrumentation only after privacy/value review.

### 8.2 P1 “showcase-quality” capabilities

These are strong targets if they prove useful rather than ornamental:

- iOS 27 tap/scribble/rectangle segmentation refinement for difficult masks;
- Siri/App Shortcuts such as “Create an ID photo” or opening a known document profile;
- Core Spotlight indexing of document profiles;
- carefully designed TipKit education for unfamiliar editing interactions;
- subtle sensory feedback for successful alignment/export states;
- optional on-device Foundation Models assistance for explaining structured warnings or answering rule questions, subject to evaluation and strict non-authoritative boundaries;
- polished App Store product page, custom Icon Composer icon, and SF Symbols-based iconography.

### 8.3 Explicitly deferred

- Android.
- iPad-specific product experience.
- macOS, web, Windows, or cross-platform clients.
- Printing fulfilment/delivery.
- Account creation and cloud photo library.
- Cross-device sync.
- Automatic clothing replacement.
- Facial retouching/beautification.
- Generative reconstruction of missing face/hair areas.
- OCR of passports or identity documents.
- Automatic government form filling.
- “100% guaranteed accepted” claims.
- Kiosk/business workflow.
- Bulk processing.
- Decorative widgets, Live Activities, or other system integrations with no clear task value.

## 9. Initial document coverage strategy

Do not launch with hundreds of profiles that have not been individually validated. Coverage expands in controlled waves.

Suggested sequence:

- **Wave A:** a small number of high-demand countries/use cases with clear official specifications.
- **Wave B:** additional passport/visa/ID formats in priority markets.
- **Wave C:** regional and specialized documents.
- **Wave D:** non-official formats such as CV, school, club, or corporate badge photos.

The exact launch-country list is a product decision to be locked after demand research and source verification.

## 10. Quality-state model

Each requirement shown to a user has one of four machine states:

- `pass` — the app can measure the requirement and the measurement is within tolerance.
- `warn` — the app can measure a risk but confidence/tolerance is not sufficient for a hard failure.
- `fail` — the app can measure the requirement and it is clearly outside the accepted range.
- `manual_check` — the app cannot safely validate the requirement and asks the user to inspect it.

No requirement should silently disappear because the app cannot test it.

## 11. Experience success criteria

### Fast path

A good source photo should feel almost automatic:

- no permission prompt before the user chooses a capability that needs it;
- no account wall;
- no generic editor tool palette;
- no unnecessary confirmation screen;
- analysis feedback appears progressively without fake percentages;
- primary action remains clear at every step.

### Native feel

The UI should:

- follow current HIG navigation, toolbar, modal, search, and menu conventions;
- use system typography and semantic materials;
- inherit Liquid Glass from native controls instead of imitating it;
- use standard Share/Print/PhotosPicker experiences;
- respect appearance/accessibility settings automatically where possible;
- feel correct in light, dark, increased contrast, large text, and Reduce Motion environments.

### Accessibility

A user must be able to complete the core workflow without precision drag/pinch gestures. Editor alternatives and understandable VoiceOver state are mandatory.

## 12. Success metrics

Before release, analytics definitions must be privacy-reviewed.

### Product funnel

- document selection → photo selected rate;
- photo selected → valid export rate;
- median time from photo selection to first export;
- percentage of sessions completed without manual adjustment;
- retake rate;
- export error rate.

### Quality

- false-pass rate in controlled validation set;
- false-fail/warning rate;
- crop dimensional error;
- head-position error against ground-truth annotations;
- segmentation defect rate across representative scenarios;
- print physical-size error after controlled printing tests.

### iOS quality

- launch/camera time-to-first-frame;
- shutter-to-analysis latency;
- UI hitch rate / responsiveness issues;
- peak image-pipeline memory;
- thermal regressions during repeated sessions;
- VoiceOver core-flow completion rate in accessibility testing;
- Dynamic Type layout defects;
- crash-free sessions.

### User outcome

Where ethically and practically collectable, optional post-use feedback may ask whether a submitted photo was accepted. This must never be represented as authoritative certification data without controlling for self-selection and unknown submission conditions.

## 13. Business-model guardrails

The original product motivation includes frustration with intrusive advertising. Therefore:

- no full-screen interstitial ads in the core photo workflow;
- preferred baseline is no third-party ad SDK at all;
- no ad/analytics SDK receives photo content;
- no dark-pattern countdowns;
- no surprise watermark shown only at export;
- pricing, if any, is clear before paid-only output is generated;
- StoreKit is the default monetization technology;
- monetization decisions remain separated from the correctness engine.

## 14. Key product risks

1. **Regulatory drift:** official specifications change.
2. **False assurance:** users may interpret automation as government approval.
3. **Segmentation artifacts:** hair, glasses, veils, skin tones, and complex backgrounds expose errors.
4. **Camera variability:** different iPhones/lenses/processing paths behave differently.
5. **Image memory pressure:** large HEIC/JPEG sources can create avoidable memory spikes if decoded naively.
6. **Print-size mismatch:** viewers/printers may scale pages unexpectedly.
7. **Children/babies:** pose and expression rules differ or are difficult to assess automatically.
8. **Accessibility:** image-centric editing can exclude users unless alternatives are designed from the start.
9. **Localization:** official document names and instructions require more than literal translation.
10. **Platform churn:** latest SDK behavior and beta APIs can change before release.
11. **AI misuse:** generative assistance can create false authority if its boundaries are unclear.
12. **Over-scoping:** adding showcase APIs or too many countries can reduce quality.

## 15. Release philosophy

The first release should be narrow, polished, and dependable.

A document profile is release-ready only when it has:

- an official or clearly authoritative source;
- review date;
- validation fixtures;
- output-dimension tests;
- composition tests where rules are measurable;
- user-facing instructions for manual requirements.

An iOS feature is release-ready only when:

- it follows current HIG guidance or has an explicit rationale for deviation;
- it works on physical supported devices;
- it has accessible alternatives where required;
- privacy implications are documented;
- performance is measured;
- it degrades safely when availability/permissions are missing.

The objective is not to ship the largest feature list. It is to make every included detail feel intentional.
